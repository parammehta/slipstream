A Million Flights, No Server

There is no free flight-pricing API left to call. So I built the search to run where the data already is: a columnar binary file in the browser, filtered, sorted and charted without a single network request while you use it. These are the measurements that shaped it, including the ones that proved me wrong.

The constraint came first

Amadeus decommissioned its self-service portal on 17 July 2026, disabled existing keys and archived its SDKs the same day. What remains for live fares is enterprise contracts and paid scrapers. The free tier that every side project used is gone.

That settles the architecture before any code gets written. If fare data can only be acquired in bulk and offline, then querying a provider per keystroke was never the design. The search has to happen where the data already sits, which means shipping the data to the client and doing the work there.

Everything below follows from that one inversion. The interesting problems stop being about network latency and start being about how fast you can scan a few hundred megabytes of RAM inside a 16ms frame.

20.0 bytes/row

A format you can read without parsing

Offers are stored in a slab: one binary buffer, each field its own typed array laid end to end, with a small JSON blob at the tail describing the layout. Strings live in dictionaries and rows reference them by integer.

Decoding is the part that pays off. The metadata names each column's byte offset, so the reader constructs typed-array views over the existing buffer and stops. No per-row object is allocated anywhere. Decoding a million offers takes 0.21ms, which is not a parsing cost so much as the absence of one.

The size surprise. I assumed compression would shrink this a lot. Brotli at maximum quality gets 1.9×, not the 3× I expected: packed binary columns are high-entropy and there is little left to find. A million offers is 9.86MB on the wire. That number, not the raw size, is what decides you shard the file per origin airport rather than shipping one global slab.
16.4ms → 8.1ms

Filters that stop re-reading the same rows

The first design kept a bitset per predicate and intersected them. Each filter scanned all million rows, so four filters scanned four million. That measured 16.4ms, comfortably over a frame, and it would have killed the whole premise.

The fix is a selection vector. The first predicate scans every row and writes the survivors into a Uint32Array. Every predicate after it only re-checks what is left. With a filter that keeps a quarter of the rows, the second pass is a quarter of the work and the third is a sixteenth.

The inner loops write unconditionally and advance the cursor by zero or one, so there is no branch for the CPU to mispredict:

Sorting is precomputed rather than repeated. A stable four-pass radix argsort builds one permutation per sort key at load, 11 to 18ms each, and switching between cheapest, fastest and earliest afterwards is just picking a different permutation.

0.02ms

Multi-city, without building the itineraries

A three-leg trip across 100,000 offers per leg has 1015 combinations. Materialising them is not a performance problem to optimise, it is a thing you must never do.

You do not have to. The cheapest itinerary is necessarily the cheapest offer on every leg. And every itinerary after that differs from one already found by a single step up on a single leg. So the candidates worth examining are always a thin frontier around what you have already emitted, and a heap over that frontier yields trips in price order.

Combining forty itineraries measures 0.02ms. The legs' own filtered queries are the entire cost of a multi-city search, at 7.30ms for three legs.

I expected this to change the file format. I said it would need a second slab version with a legs table. It needed nothing. An itinerary is a composition produced at query time, not a kind of row, and once that was clear the feature added one kernel and no migration.
161ms → 2ms

What the worker actually buys

Moving the engine into a Web Worker is the obvious architecture, but at the size the demo ships it is close to a wash, and saying so is more useful than claiming a win. The page sends filters and a window; it receives counts, charts and a packed array of only the rows about to be painted.

At 500,000 rows the worker halves the blocking and costs about 9ms of added latency to do it. At three million it is the difference between a page that responds and one frozen for a sixth of a second on every pointer move. Notice that the two main-thread numbers are identical at 3M: when the engine runs inline, the engine time is the block. The demo keeps the worker because the architecture should hold at the sizes the design exists for, and exposes ?engine=inline so anyone can check the claim.

1.7GB → 67KB

Fares that someone actually paid

Generated prices would have undermined everything else, so the fares come from the US DOT's Airline Origin and Destination Survey: a 10% sample of tickets sold by US reporting carriers, published quarterly, public domain, no account and no rate limit.

The harvester streams 1.7GB in two passes, one to rank 65,100 directional markets by traffic and one to build fare curves for the busiest 1,200. Each market keeps its observed spread as nine deciles rather than an average, because the gap between a cheap seat and an expensive one on the same route is the interesting part. The result is 67KB.

That table is the validation. JetBlue and Delta splitting the JFK transcon, a p90 up at $1,103 where the premium cabins sit, Hawaiian leading Los Angeles to Honolulu, Republic flying regional for the majors out of LaGuardia. None of it was put there.

Departure times are a different matter and the README says so plainly. DB1B records what was paid and how far the passenger flew, never when they left, so schedules are generated from distance with the connection rate taken from each market's own observed share. Fares, routes, carriers and carrier mix are data. Clocks are not.

five corrections

What measurement kept telling me

The useful pattern in this project was how often a confident assumption turned out to be wrong in a way that only a number could reveal.

I assumed Scrolling to the end of 500,000 rows would hit a performance cliff. It measured 0.63ms at offset 499,000. A tight loop over a typed array is simply fast. I did not optimise it.
I assumed The browser caps element height around 33.5 million pixels. It is 224, measured at 16,777,214. My spacer silently shortened and the last 53% of results were unreachable. The fix maps scroll position using the DOM's real range instead of a constant I believed.
I assumed Compression would do most of the work on the wire. Brotli got 1.9×. Packed columns have little redundancy left, which changes the delivery plan from one file to per-origin shards.
I assumed Multi-city would need a second version of the file format. It needed none. Itineraries compose at query time.
My benchmark said Multi-city search costs about 5.5ms. The live page showed 58ms. The benchmark used broad legs; a real leg is one route on one day, around fifty rows out of half a million, and finding its cheapest offers walked the entire global price order. Sorting the narrow selection directly brought it to 2.94ms. The benchmark had been measuring the wrong shape of query and hiding a twentyfold regression.

The last one is the one I would keep. A benchmark that measures a plausible-looking case rather than the real one does not merely fail to help, it actively reassures you while the product is slow.

125 tests

Where it ended up

About 2,300 lines of dependency-free TypeScript, run through Node directly rather than compiled. The demo is a single 179KB HTML file with the engine inlined, because ES module imports are blocked on file:// origins and the page should open from disk. That file is generated from the same source the tests run against, and a staleness check fails the build if the two drift.

It generates 500,000 offers over the harvested markets, filters and sorts and charts them locally, builds multi-city itineraries, and encodes every view into a shareable link. While you use it, it makes no network requests at all.
